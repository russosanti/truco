## PRD 3 — envido

- **Pure math** in `src/envido_rules.lua` (`envidoValue`/`envidoWinner`/`rejectValue`/`faltaEnvidoValue`); throwaway `EnvidoAiStub` (open if ≥27, quiero if ≥24, never raises).
- **Falta modeling (not spelled out in the PRD):** `cumulative` tracks only envido(2)/real(3); falta is a ceiling that adds nothing. Accept-falta pays `faltaEnvidoValue` (ignores cumulative); reject-falta pays `max(cumulative,1)` = the pre-falta pot floored at 1 (direct falta→1, Envido→Falta rejected→2). Non-falta reject uses `rejectValue(cumulative,lastCallValue)`.
- **Reusable call engine:** `src/canto.lua` is a family-agnostic call/response/escalation state machine (`Canto`), config-driven — tracks calls/cumulative/caller/responder and yields a structured `outcome`. `src/envido_canto.lua` binds it to envido: the `ENVIDO_CANTO` ladder config + `envidoAward(outcome, mano, ...)` → (side, points) via envido_rules. Tested in `src/canto_test.lua`. (PRD 4 evaluated it for truco and deliberately did **not** use it — see below.)
- **Envido lives inside trick 1, NOT a separate phase.** The old `CantosState` was **deleted**; machine is now `deal → trick → score`. Rationale (user): "play a card = pass" only makes sense if the envido window and the first trick are the same moment. In `TrickState`: envido is callable while `tricksPlayed==0 and not envidoUsed`, at each side's turn before it plays its first card — mano first, and the **pie can still call after mano's card** (correct reglamento; verified in the flow driver). Opening a call sets `self.canto`; while set, it owns input/render (Quiero/No quiero/raises) and pauses card play; `finishCanto` applies points **immediately**, shows a 1.5s banner, then clears `self.canto` and the *same* `currentPlayer` resumes to play their card. AI envido decisions reuse the 0.6s think guard.
- **No Pass button (user):** to decline envido you just play a card. Human open turn shows Envido/Real/Falta buttons **and** the playable hand; clicking a card plays it (declines). Buttons are mouse+keyboard (`[n]` shortcut), reusing `pointInRect`/`drawButton`.
- **Harness impact:** `driveKeys` in `smoke.lua`/`rotation.lua` now detects TrickState (`cur.tricksPlayed`) and answers an AI call with No quiero (`'2'`), else plays a card (Right+Enter) which also declines the human's own envido. Flow verified in `scratchpad/envido.lua` (human open accept/reject, AI-opens + human raises Real, falta malas, both-play-to-decline, click-driven open).

## PRD 4 — truco

- **Reconciliation (important):** PRD 4 is written around `CantosState` + shared `loop.truco*`, but PRD 3 deleted `CantosState`. So truco, fold, and the envido interrupt all live in `TrickState`, and — since it no longer spans two states — truco is **state-local** (`self.trucoLevel`/`trucoLeader`/`trucoPending`), **not on `loop`**. `HandScoreState` is now truco-agnostic: every path into `score` passes explicit `{winner, points}` (normal trick resolution computes `trucoLevel>0 and trucoLevel or 1`; reject/fold pass their own value), and score just awards them.
- **Architecture decision (user asked for the cleanest):** truco does **not** reuse the `Canto` engine. Canto encodes envido's cumulative-pot + in-response-raise semantics; truco is level-based (2/3/4), persists across tricks, is accept-before-raise, and the accepted level must outlive the negotiation. Forcing it through Canto would use the abstraction's shell not its substance. Truco reuses the *patterns* (buttons, 0.6s AI-think, banner) but keeps its own tiny state. `src/truco_rules.lua` = pure math/gating (`trucoRejectValue`=level-1, `trucoFoldValue`, `availableTrucoCall` gating), tested in `truco_rules_test.lua`. `TrucoAiStub` = call/raise iff holds a brava (tier≤4), respond quiero iff brava-or-won-a-trick, never folds.
- **Interrupt = trivial with two independent slots:** a pending truco is `self.trucoPending`; envido runs on `self.canto`. "Envido primero" (offered only when `canInterruptEnvido`: trick 1, nothing played, envido unused) opens an envido canto while the truco pending just sits there; when envido resolves + banner clears, the still-set `trucoPending` is answered (Quiero/No quiero — no second interrupt, envido now closed). No nesting/stashing.
- **Accepting truco closes envido (user rule):** `canCallEnvido`/`canInterruptEnvido` both require `trucoLevel == 0`. Once a truco is accepted, envido is gone for both sides — the interrupt (before answering the first truco) is the *only* way envido coexists with truco ("envido esta primero", to avoid skipping it). The interrupt is **symmetric**: the human gets an "Envido primero" button; the AI, in `aiRespondTruco`, takes envido first too when it holds a strong envido (`EnvidoAiStub.chooseOpen`) before answering the truco. Both directions verified in `scratchpad/truco.lua`.
- **AI order:** `updateAiTurn` tries truco first (so an AI-mano with a brava opens the hand with truco, making the interrupt reachable), then envido, then a card. Accept only sets the stake (`trucoLevel`, `trucoLeader = accepter`); points land at hand end. Reject/fold end the hand immediately via `machine:change('score', {...})`.
- **Verified:** `scratchpad/truco.lua` (accept sets stake; reject §7 values 1/2/3; fold = level-or-1; normal scoring path awards the stake; full interrupt end-to-end). `truco_rules_test.lua` passes. smoke now shows truco firing (AI opens on bravas, human declines).

## PRD 5 — chico / partida

- **One scoring funnel (§3, the whole point):** `HandLoopState:awardPoints(side, points)` is now the *only* place `humanScore`/`aiScore` change, and it runs `chicoWinner` on every award. Necessary because points land from **two** places — `HandScoreState:enter` (trick/truco) and `TrickState:award` (envido, which can pay out mid-trick-1). A falta envido crossing 30 would have slipped past an end-of-hand-only check. Returns `true` when the chico ended, so `HandScoreState:enter` can `return` instead of arming its next-deal timer.
- **Stale-continuation guard (subtle, would have been a real bug):** aborting mid-hand orphans a `TrickState` with timers still armed (AI think, `resolve`'s 1.0s pause → `machine:change('score', …)`), which would score into the *next* chico. **`Timer.clear()` is not usable here** — we'd be calling it from inside a Timer callback, and `lib/knife/timer.lua` caches `#group` before iterating (`Timer.update`) while `detach` indexes `group[#group]`, so clearing mid-pass crashes twice over. Instead `HandLoopState:changePhase(name, params)` no-ops while `handAborted`, and **all six** `loop.machine:change` sites in the phase states (1 DealState, 4 TrickState, 1 HandScoreState) now go through it. Only `awardPoints` and `ChicoScoreState` call `machine:change` directly — they're the two allowed to move past an abort. A stale `playCard` on the orphan is harmless (`DealState` reassigns `loop.humanHand`/`aiHand` wholesale; nothing renders the orphan's anims).
- **`src/match_rules.lua`** — pure: `chicoWinner` (`>=CHICO_TARGET`, deliberately not `==`, since falta/truco overshoot), `chicosNeeded` (1 / 2), `partidaWinner`. The `2 of 3, 3rd decisive at 1-1` rule needs no special case: 1-1 fails `>= 2`, and whoever takes the 3rd necessarily reaches 2.
- **`ChicoScoreState`** = a 4th *phase* in the loop's machine (not the stack), so it renders through `drawHud` like the others. Holds 2.5s, then either `gStateStack:pop()` + `push(MatchEndState(winner, loop))` or `loop:startNextChico()`.
- **Dealer across the chico boundary (user):** keeps alternating (`startNextChico` flips it and bumps `handNumber`) rather than a fresh coin flip per chico. A real re-cut would re-randomize, but unbroken rotation keeps `scratchpad/rotation.lua`'s "dealer flips every hand" invariant meaningful.
- **`MatchEndState`** reads its tally off the loop once in `init` (the loop is popped, so nothing live is held): `best_of_3` shows chicos, `single_chico` shows the final score. Enter → pop + `push(StartState())`.
- **StartState temp keys (throwaway, PRD 7 replaces):** Enter = `best_of_3`, `s` = `single_chico` — otherwise `single_chico` is unreachable in-game before the menu exists.
- **Harness impact:** `envido`/`truco`/`stack` hand-rolled fake loops gained `awardPoints`/`changePhase` stubs. `smoke.lua` needed a `gStateStack` stub *and* delta-accumulated hand/point counters (scores reset per chico, `handNumber` per match); `rotation.lua` breaks out when a match ends (a new match re-coin-flips the dealer, legitimately not a flip). New `scratchpad/match.lua`: (a) chico resets + deals on, (b) 1-1 → decisive 3rd → `MatchEndState` 2-1, (c) Enter → StartState, (d) single_chico ends at chico 1, (e) mid-hand falta chico — `tricksPlayed` stays 0, no leaked points, and `changePhase` asserted a no-op while aborted.

## PRD 6 — heuristic AI

- **Reconciliation — signatures had to grow.** PRD §2/§9 promises "no call-site changes", but the old signatures physically can't carry what §4-§6 need: `chooseCard(hand)` can't see the opponent's card or the trick score, `wantsToCall(hand)` can't see `tricksPlayed`/`trucoLevel`, `chooseResponse(value)` can't express a raise, and **fold is an entirely new decision point** nothing was asking about. Each entry point now takes a `ctx` table built by one place, `TrickState:aiContext()` (`against, myWins, theirWins, tricksPlayed, trucoLevel, myScore, theirScore`). One table rather than positional args is what actually delivers §2's intent — later PRDs add fields without reshaping call sites. Filenames kept per §9, so `*Stub` is now a misnomer.
- **`src/ai_config.lua`** — `{ aggression = 0.5, bluffRate = 0.10, random = math.random }` + `chance`/`coin`/`bluffDelta`/`shiftTier`. **Aggression and bluffing are the same primitive**: both just step a tier along an ordered ladder (`shiftTier`), which is what lets §5's numeric bands and §6's categorical positions share one knob. `random` is an injectable seam purely so tests can kill the coin flips (`AiConfig.random = function() return 0.9 end`); production leaves it alone. This is the one file PRD 7 edits per tournament round.
- **`AiStub` (§4) is deterministic** — §4 defines no bluffing, and a randomized card play reads as a blunder, not deception. Responding: weakest winner → weakest tie → weakest overall. **Leading extends §4's table with the parda case:** §4 only names "either side has a trick win", but by `isHandDecided` a parda plus any single win also settles the hand, so `tricksPlayed - myWins - theirWins >= 1` counts as decisive too — leading small into a decider would throw it away.
- **`EnvidoAiStub` (§5):** `tier(value, aggression)` is pure/public, boundaries `20/27/31` shifted down by `(aggression-0.5)*8` (0 → 24/31/35, 1 → 16/23/27). Exceptional opens **Falta when `wantsFalta` = leading and past 15** (`faltaEnvidoValue` pays `30 - leader` there, so winning it closes the chico), else a coin flip between Real and Falta — the user's rule. `chooseResponse` takes the canto's `availableRaises()` so it can only name a legal escalation; **the ladder's own narrowing is what bounds escalation** (once falta is down the list is empty → quiero/no quiero only), so "raise once" needs no counter.

A weak envido still lets truco open the hand, which is what keeps the human's "envido primero" interrupt reachable. Then truco → plain envido → fold → card.
- **`aiRespondCanto` gained a raise branch** (`canto:raise` + `showAiMessage`) — safe under the announce-before-award rule since a raise pays nothing. The fold announces first and owns the phase change in its `afterFn` (`'Me voy al mazo'`), same as a truco no quiero.
- **Verified in play, not just in units.** Instrumented soak runs over the real `HandLoopState` confirmed each §7 manual check: 21 covers with **0 overspends**, bravas held at 0-0, strongest led on deciders, envido quiero/no quiero/raise-to-Real/raise-to-Falta all occurring, and **7 folds against 34 "held on"** (so it folds selectively). Two soak zeros were driver artifacts worth remembering: the fold path is unreachable unless the *human* calls truco (an AI-called truco implies the AI was strong, and `myWins > 0` pins it strong forever), and `chooseResponse` only runs when the human opens the envido.
- **Driver re-rigging:** `envido.lua` hands were picked against the old ≥27/≥24 thresholds and now land in different tiers — several were re-rigged to **decent (20-26)**, the only tier that plainly accepts without raising (`copas_4/copas_2/bastos_5` = 26). Both flow drivers set `AiConfig.bluffRate = 0`; `smoke`/`rotation` deliberately leave bluffing live. **Scenario (h2) became unreachable as written** (a decent AI-mano now opens envido itself instead of declining by playing) and was re-routed through the interrupt: an AI-mano with a brava + envido 26 opens *truco*, the human answers Envido, and the AI's merged `Quiero, 26` follows. New cases: envido (j) the AI raising, and two truco fold cases (folds at a stake, plays on without one). smoke 44 → 41 hands (folds end hands earlier).

- **`HandLoopState` now takes an options table** — `HandLoopState{ matchFormat, aiName, onMatchEnd }`, all optional. This **supersedes the PRD 7 note** where I insisted on the positional string: at three params (two optional) the table is what both PRD 7 §5 and PRD 8 §4 actually write, and positional args stop reading. A bare `HandLoopState()` is still a standalone best-of-3 vs "AI" returning to the menu.
- **`src/opponent_names.lua`** — the two 16-entry pools from §3. `randomName(exclude)` retries on collision as specified. **`generateNames(n)` deviates from "call randomName n times":** it shuffles a copy of the first-name pool and takes `n`, pairing each with a random surname. Same guarantee for full names, *plus* distinct **first names** — which is what the bracket displays, and a repeated first name there would be genuinely ambiguous. No retry loop either. 16 first names covers the 15 opponents a tournament needs.
  - **Three display forms would be too many, so there are two:** `aiName` is the full name (match-end title, tournament callout); `firstNameOf(name)` is the in-match short form (HUD, dialog prefixes, trick/hand/chico banners) where a 19-char name would not fit. ## Addendum — bracket tree + matchup screen

- **Two facts made this small, both verified before writing any code:**
  - **The loser of a decided round is already derivable** — round `r` match `m` feeds round `r+1` slot `ceil(m/2)`, `((m-1)%2)+1`, so whoever sits there won and the other lost. That's `matchWinner(bracket, r, m)` in `tournament_bracket.lua`: pure, read-only, **no data-model change**, and `nil` for any round `advanceRound` hasn't produced yet — which *is* the "never reveal a result early" rule rather than a separate guard.
  - **`slotXY`'s doubling spacing already lines the tree up.** Each pair's midpoint is exactly the next round's row (36.5 / 54.5 / 72.5 / 90.5), so the connectors needed no layout of their own — just stubs at `(r-1)*96+56` → `r*96-6` and a feed into `r*96+2`.
- **`phase` gained `'matchup'`** between `'bracket'` and the match. `matchFinished(true)` on a non-final round now sets `phase = 'bracket'` after `advanceRound`, so a win lands back on the tree with the round just decided filled in — not on the next matchup. The champion and eliminated paths are untouched (PRD 8's behaviour, as the addendum specifies). One Enter can't skip a phase: `update` takes one branch per frame and `main.lua` clears `keysPressed` every frame.
- **Losers are dimmed to 0.3 alpha, not deleted** (the addendum's point: seeing who didn't make it is half of what a bracket is for). Greyed rather than struck through — a strike line through 8px text is illegible at this resolution. The human stays gold throughout, dimmed only if they're the one who went out.
- **Rounds not yet reached draw `-` placeholders**, with the slot count derived (`2^(4-r)`) rather than invented from data that doesn't exist yet.
- **Harness:** `scratchpad/tournament.lua`'s four match starts now go through a `startMatch(ts)` helper that asserts `bracket` → `matchup` → match, which doubles as the regression test for the new screen. New cases: (a3) `#bracket.rounds == bracket.round` at every step plus "every decided match has exactly one winner and one dimmed loser", and (a4) the connector x-ranges staying inside the column gap with every round's tree actually drawn. The `matchWinner` derivation also got unit cases in `tournament_bracket_test.lua` (decided vs. undecided rounds, and agreeing with `advanceRound` for a human win *and* a human loss).
- **Verified by dumping the drawn grid** (no screenshots in this environment): on entry, round 1 holds 16 names and rounds 2-4 are all placeholders; after the R16, each pair reads winner + `(out)`, the winners sit on the correct midpoint rows of the Quarterfinal column, and the human's row moves 68 → 72.5 across columns.
- **Held-click bug: clicking "Tournament" skipped the bracket (user).** The flow was already `bracket → matchup → match`, but a *mouse* click never showed the tree. Cause: a real click stays held for several frames, and `TournamentState:init` set `mouseWasDown = false`, so on its very first update the still-held button read as a fresh press and advanced straight to the matchup screen. Keyboard was unaffected — `main.lua` clears `keysPressed` every frame and only the top state updates, so an Enter can't carry across a push; the mouse is *polled*, not evented, so it can. Fix: seed `mouseWasDown = love.mouse.isDown(1)` at construction, so only a genuinely new press counts. Applied to all three states with click edge-detection (`TournamentState`, `MenuState`, `TrickState`) — same latent bug, one line each, and no behaviour change for the drivers (their stubbed `isDown` returns false at init anyway). Regression case (a5) in `scratchpad/tournament.lua` drives the real MenuState click with the button held for 6 frames and asserts the phase stays `bracket`, then that a released-and-pressed-again click does advance.
- **Names are unaccented (user):** Tomas not Tomás, Gomez not Gómez — 11 of the 32 pool entries changed. Beyond the look, this makes the width budgets honest: `firstNameOf` and the bracket/dialog sizing count *bytes*, and an accented character is two bytes in UTF-8, so "Tomás" measured as 6 where it draws as 5. All 32 entries and 500 generated names verified plain ASCII; longest first name is now `Valentina` at 9 chars (~54px), inside the 56px bracket-column budget.

The escalation alternates naturally because the new pending is owed by the other side, so **nobody waits for their turn and no card is played in between** — verified end to end through the real buttons: `AI: Truco → human Retruco → AI: Vale cuatro → human Quiero`, stake 4, `playCount == 0` throughout.
  - Reject values needed no change: `trucoRejectValue(3) = 2` is exactly "you refused my retruco, so I take the truco's 2". Fold likewise reads the banked `trucoLevel`.
  - `TrucoAiStub.respond` can now return `'raise'` (PRD 6 §6's "raise if very strong" = **2 unplayed bravas**); `aiRespondTruco` honours it only when `trucoRaiseCall` says it's legal, so at Vale cuatro it degrades to a plain quiero. ## PRD 9 — flor

- **The existing `Canto` engine took flor with ZERO changes**, which was the thing worth checking first. Flor's rungs are *fixed* (3 / 6 / al resto), not additive like envido's, but `outcome.lastCallValue` + `outcome.ceiling` already carry everything the award needs — `cumulative` is just meaningless here, exactly as envido's falta ceiling already ignores it. So `flor_canto.lua` is a config plus `florAward`, mirroring `envido_canto.lua`.
- **The user's ruling made flor structurally identical to envido** (supersedes PRD §6's "nothing to reject" at the base): *one calls flor, the other says quiero / me achico / contraflor; then the first says quiero / me achico / al resto*. Every rung is accept/reject/raise — the exact three-way shape `self.canto` already drives. So **flor and envido share the negotiation slot**, with `self.cantoFamily` picking the labels, the AI stub and the award. One input path, one reveal, one slot. A base-level "me achico" pays the flor's own 3, so the single formula `ceiling and 6 or 3` covers every rung.
- **Contraflor is 6** (user confirmed §3's pick over the glossary's 3). Al resto pays `faltaEnvidoValue(...) + 2*3` — the falta plus both declared flores.
- **A strict ladder** (flor → contraflor → al resto, no jumping straight to the ceiling) is what makes §6's reject column exact: each rung's refusal pays the rung below it.
- **`enter()` is new and load-bearing.** Flor can't resolve in `init` — `init` runs *inside* `StateMachine:change`, so an award there that ends the chico would have its `machine:change('chico')` overwritten by the outer `self.current = ...` assignment. `enter()` runs after that assignment, and the award sits behind the announcement's `Timer` anyway, so neither path can re-enter.
- **`update` needed exactly one line** — `if not self.florResolved then return end`, placed *after* the dialog/canto branches (so the flor canto drives itself through the machinery that already exists) and *before* truco and the turn logic.
- **The envido lockout is two conditions**, `and not self.florHappened` on `canCallEnvido`/`canInterruptEnvido`. Verified over 20000 real deals: 0 violations either way (no envido in a flor hand, and envido always available without one).
- **`revealEnvido` became `revealShowdown(family, manoPrefix, onDone)`** — extracted, not rebuilt, per §6. The only difference between the two families is which pair of values is compared, so `cantoValues(family)` is the whole of it.
- **`FlorAiStub` always accepts at the base**: §8's 28 threshold is explicitly for refusing a *Contraflor*, and conceding the base costs the same 3 as losing the comparison, so declining there is strictly dominated. A 34+ flor answers a Contraflor by going **al resto** rather than merely accepting — my first driver case asserted a plain accept and was wrong about the AI, not the other way round.
- **Frequencies (20000 deals):** no flor 90.3%, one side 9.38%, both 0.27%. The both-flor contest is rare enough that `scratchpad/flor.lua` rigs it directly; a natural soak over 37 hands saw 3 flor hands and no both-flor, as expected.
